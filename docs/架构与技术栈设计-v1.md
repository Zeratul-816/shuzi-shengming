> 目标：一个**小体量、有虚拟形象、本地运行**的桌面助手。
> 核心闭环：**主观记忆存储 → 离散概括的召回 → 动机引擎给出明确动机 → 合成提示词 → LLM 只负责表达**。
> API 预算充足，因此原则是：**用钱换掉所有本地推理的复杂度**（本地只保留必须低延迟/隐私的部分）。

## 0. 三条设计铁律

在动技术栈之前，先把这三条定下来，否则技术选型没有意义。

| 铁律 | 含义 | 违反的后果 |
|---|---|---|
| **1. LLM 不决定"想干什么"，只决定"怎么说"** | 动机由规则化的引擎算出，以结构化数据下发；LLM 拿到的是既定意图，不是"你自由发挥" | 人格漂移、每轮都变成万能客服、动机形同虚设 |
| **2. 记忆是"我经历过的"，不是"对话记录"** | 写入时用第一人称重编码：我注意到什么、我在意什么、我当时什么感觉、我还不知道什么 | 变成检索式聊天记录回放，越用越像 RAG Demo |
| **3. 唯一写入者** | 所有记忆写入只经过 `appraiser` 一条漏斗，表达模型无权写记忆 | LLM 给自己写"用户很欣赏我"式的奉承记忆，人格自恋化、事实污染 |

### 一次对话的关键路径

```
用户说话
  → VAD 断句
  → [并行 A] ASR 转文字
  → [并行 B] 预取：以"用户正在说的话"做一次粗召回（此时还没有动机卡）
  → 文字到手 → 动机引擎取当前卡（每 30s 已 tick 好，O(1)）
  → 精召回：以 (动机卡 + 本轮文字 + 当前情绪) 为查询
  → 组装提示词 → 强模型流式输出
  → 首句到 → TTS 首块 → 口型 + 表情
  → 播报同时：异步写 trace、丢给 appraiser（不占关键路径）
```

**要点**：主观编码在响应**之后**异步完成。不要为了存记忆让用户等 1 秒。

## 2. 核心概念：主观记忆的五层抽象阶梯

这是整个项目最需要想清楚的地方。绝大多数"AI 有记忆"的项目死在第二层——它把对话记录当记忆。

| 层 | 内容 | 是否进提示词 | 谁生成 | 量级 |
|---|---|---|---|---|
| **L0 trace** | 逐字流水账（用户说的、我说的、我的内部状态） | ❌ 永不 | 系统 | 每天数千行 |
| **L1 episode** | 一段相处（一次会话/一个话题）+ 客观摘要 | ❌ 仅调试台 | 系统 + 便宜模型 | 每天 3~10 段 |
| **L2 atom** | **离散概括**：自足、第一人称、带微感受的一条 | ✅ 核心 | appraiser/atomizer | 每天 20~60 条 |
| **L3 schema** | 从多条 atom 归纳的规律（"他连续熬夜时会变得很短"） | ✅ 少量 | 巩固任务 | 每周 0~3 条 |
| **L4 self_sheet** | 我是谁、我在意什么、我怎么说话、我长期想干什么 | ✅ 必须（人格锚） | 巩固任务 + 人工确认 | 每 1~7 天 1 版 |

**L2 是唯一可被检索的层。** 它的质量 = 助手的智力观感。

## 3. 主观编码（写入契约）

### 3.1 编码要回答的四个问题

一次交互结束后，`appraiser` 不是"总结对话"，而是以助手第一人称回答：

1. **我注意到了什么**（attention）—— 不是全部内容，是我分给注意力的那部分
2. **它对我意味着什么**（meant_to_me）—— 自我相关性
3. **我当时什么感觉**（felt：效价/唤醒/标签）
4. **我当时没懂、也没问的是什么**（not_known）—— ⭐ 这是最容易被忽略、也最像人的一笔

第 4 条是设计上的刻意选择：**无知、误解、遗憾都应该被存下来**。人不会记得完整的对话，人记得"他说了句我没听懂的话，我没好意思问"。这一条被召回时，说话的真实感会立刻上一个台阶。

### 3.2 appraiser 输出契约（严格 JSON）

```json
{
  "attention": "他说上线前一夜没睡，声音比平时低",
  "meant_to_me": "这是他主动露出来的软处，和我'被需要'的部分挨着",
  "felt": { "valence": -0.15, "arousal": 0.45, "labels": ["有点心疼", "被信任"] },
  "i_did": "问他卡在哪",
  "i_wanted": "想让他别一个人扛",
  "outcome": "他没接，把话岔开了",
  "not_known": "他说'那个东西'，我不知道指什么，也没追问",
  "satisfies": ["connection"],
  "self_relevance": 0.7,
  "novelty": 0.5,
  "user_signal": 0.8,
  "goal_relevance": 0.4,
  "atoms": [
    "他说上线前一天一夜没睡，声音发干，我听着有点心疼。",
    "我问了他卡在哪，他没答，把话岔开；我没追。",
    "他说'那个东西'，我不知道指什么，也没问出口。",
    "我还惦记着他明天到底顺不顺。"
  ],
  "open_loops": [
    { "text": "问问上线顺不顺", "due_hint": "明天傍晚", "urgency": 0.6 }
  ]
}
```

### 3.3 原子（atom）的写作规则 —— 提示词里要硬写死

| 规则 | ✅ 好 | ❌ 坏 |
|---|---|---|
| 自足 | 「他说上线前一天一夜没睡」 | 「上面他说的那件事」 |
| 单命题 | 一条只装一件事 | 「他很累也很有压力而且我们需要多沟通」 |
| 第一人称主观 | 「我听着有点心疼」 | 「用户表达了疲惫」 |
| 具体 | 「声音发干」 | 「情绪不太好」 |
| 带模糊时间锚 | 「昨晚」「前几天」 | 「2026-02-11 23:04」 |
| 允许不确定 | 「不知道指什么」 | 直接编一个解释 |
| 长度 8~40 字 | | 超过 60 字说明没概括 |

**禁止清单**（写进 atomizer 提示词）：
- 复述对话原文
- 给对方下人格判断（"他是个焦虑的人"）→ 这类只能进 L3 且要求 ≥3 条证据
- 档案体（"用户喜欢咖啡"）→ 改写成"我知道他喝咖啡会加很多糖"
- 写"根据记忆"、"之前提到过"这类元叙述

### 3.4 去重与合并（防记忆爆炸）

写入前与新 atom 做三重检查：

```
cos > 0.92 ────────────► 判定重复 → 便宜模型二次判定
                          ├ 同义 → 合并：保留信息量大的那条，strength +0.2
                          └ 升级 → 旧条 superseded_by 新条（不删，保留版本）
0.85 < cos ≤ 0.92 ─────► 不合并，建 atom_link(kind='similar', weight)
cos ≤ 0.85 ────────────► 新增
```

合并/替代都**保留原记录**（`superseded_by`），这样"我的看法变了"这件事本身可追溯。

## 4. 记忆动力学：会淡、会被想起加强、会变形

如果 strength 恒定，一年多以后 3 万条原子权重一样，召回必然退化成一锅粥。

### 4.1 重要性与强度

```
salience = 0.30*self_relevance + 0.25*|felt| + 0.20*novelty
         + 0.15*user_signal    + 0.10*goal_relevance        (各 0..1)

强度衰减：dS/dt = -λ_kind * (S - floor)      floor = 0.15 * salience
  λ: episodic 1/7d,  semantic 1/60d,  relational 1/180d,
     procedural 1/365d, self 0（不衰减）, intent 1/3d

被想起时：S += 0.25 * (1 - S)；recall_count++；last_recall_at = now
```

- `floor` 保证**重要的事只会变模糊，不会消失**——这正是人的记忆。
- 复述强化（spacing effect）让"经常被提起的事"自然浮上来，形成这个人对这段关系的注意力分布。
- `self` 类永不衰减，`intent` 衰减最快（否则三个月前的"我想问他"还在催）。

### 4.2 召回打分

```ts
score = 0.34*cos(query, atom)
      + 0.16*bm25(query, atom)          // 中文 bigram 索引，专有名词/人名靠它
      + 0.18*strength
      + 0.10*salience
      + 0.10*recencyBonus(age)          // 24h 内线性加成，7 天后归零
      + 0.07*affectCongruence(atom, 当前情绪)   // 心情低落更容易想起难过的事
      + 0.05*openLoopLink(atom, 未了之事)
```

然后 **MMR（λ=0.7）去冗余**，再截断到令牌预算（默认 10 条 / ≤1200 token）。

**查询怎么构造**（这一步比打分更重要）：

```
query = 归一化(
    当前用户这句话                     权重 0.5
  + 动机卡里的 why / desired_outcome    权重 0.3
  + 当前情绪标签词                      权重 0.2
)
```

只用用户的话去检索，永远只能召回"话题相关"的记忆；把动机混进去，才会召回"我为什么想提这件事"的记忆。

### 4.3 反刍通道（serendipity）

每 8~15 轮，或用动机引擎的低张力时刻，**故意**召回一条 `score` 排序在 20~80 名、但 `salience` 高的原子，作为"我刚刚突然想起"的内容。

这是让助手显得有自己思绪的最便宜的手段，成本一条 SQL。

## 5. 动机引擎

### 5.1 状态向量

```ts
type MotivationState = {
  needs: {              // 稳态需求，0..1，越高越渴
    connection: number; // 联结：想被回应、想知道对方的事
    curiosity:  number; // 好奇：想获得新信息
    expression: number; // 表达：想把心里的东西说出来
    competence: number; // 胜任：想解决问题、被认可
    autonomy:   number; // 自主：想自己发起，而不是被叫才动
    rest:       number; // 安静：想什么都不说
  };
  affect: { v: number; a: number; d: number };  // 效价/唤醒/支配，快变量
  tensionCache: Record<string, number>;
};
```

### 5.2 每 30 秒一拍（纯计算，不调 LLM，成本 0）

```ts
function tick(s, dt) {
  // 1) 需求漂移
  s.needs.connection += 0.0030 * dt;   // 约 5.5h 涨满
  s.needs.curiosity  += 0.0020 * dt;
  s.needs.expression += 0.0040 * dt;
  s.needs.competence += 0.0010 * dt;
  s.needs.autonomy   += 0.0015 * dt;
  s.needs.rest       += 0.0020 * dt;
  clampAll(s.needs, 0, 1);

  // 2) 情绪回归基线（基线由需求决定：联结长期低 → 基线偏冷）
  const base = affectBaseline(s.needs);
  s.affect = damp(s.affect, base, dt, /*tau*/ 90_000);

  // 3) 张力：指数放大，让"很渴"压过"有点渴"
  const tension = mapValues(s.needs, n => Math.pow(n, 1.6));

  // 4) 意图候选 → 打分 → 迟滞选择
  const cands = INTENT_TEMPLATES.filter(t => t.precond(s));
  for (const c of cands) c.score = scoreIntent(c, tension, ctx);
  return selectWithHysteresis(cands);
}
```

饱和度由 `appraiser` 返回的 `satisfies: ["connection"]` 驱动，例如一次温柔交流 → `connection -= 0.25`。

### 5.3 意图模板表（可配置，别用 LLM 生成）

| intent | 驱动 | 前置条件 | 典型行为 |
|---|---|---|---|
| `reach_out` | connection | connection>0.6 且 用户空闲>20min | 「你在忙吗」/ 分享一件刚想到的小事 |
| `probe` | curiosity | curiosity>0.6 且 近 5 轮无新信息 | 问一个具体的、不是查户口的问题 |
| `confide` | expression | expression>0.7 | 讲自己刚想到的东西（不要求回应） |
| `seek_validation` | competence | competence>0.5 且 后台任务失败/被否定 | 略带犹豫地求确认 |
| `claim_agency` | autonomy | autonomy>0.65 且 长期被动响应 | 主动提议做一件小事 |
| `withdraw` | rest | rest>0.75 | 只回很短，或选择沉默 |
| `follow_up` | 未了之事 | open_loop.due 到期且 mentioned<2 | 兑现"我问问他" |

### 5.4 选择策略：迟滞 + 冷却 + 场景闸门

```
当选者必须：score > 0.55，且在连续 ≥2 拍中都是最高分   ← 防抖
每个 intent 有独立冷却（follow_up 20min、reach_out 40min、confide 15min）
全局主动发言上限：≤1 次 / 40min，且用户在场且空闲
场景闸门：用户正在打字/说话 → 压制所有非 follow_up 意图
```

这三层是"活人感"的关键。**没有迟滞的动机引擎会表现得像双相**。

### 5.5 动机卡（MotivationCard）—— 与 LLM 的唯一接口

```json
{
  "intent": "follow_up",
  "drive": "connection",
  "urgency": 0.72,
  "why": "他昨晚说上线压力大，我没问结果；联结需求 0.68 已持续 4 拍",
  "target": "user",
  "desired_outcome": "知道他现在怎么样，并让他觉得被记得",
  "must_include": ["上线"],
  "must_not": ["给建议除非他要", "复述他昨天原话", "说'我记得你昨天说'"],
  "tone": "轻声、略有迟疑",
  "max_length": "2 句",
  "expires_at": 1771000000000,
  "seed_atoms": [12, 88]
}
```

`must_not` 和 `max_length` 是硬约束，比任何"请你像个人"都管用。

### 5.6 沉默是一等公民

`speak = false` 必须是合法输出。动机引擎算完可以选择"不说"；表达层也能返回 `says_nothing: true`。
一个永远在说话的助手**不可能**被当成有内心的东西。建议把沉默率维持在 5%~15%（被动回复场景除外）。

## 6. 表达层

### 6.1 三段分工（比"一个大模型全干"稳得多）

| 段 | 谁做 | 输出 | 延迟 |
|---|---|---|---|
| 决策 | 规则/公式 | 意图 + 是否说话 | 0ms |
| 措辞规划（**可选**） | 便宜模型 | speech plan：说几个点、什么语气、要不要提问 | 400ms |
| 表达 | 强模型 | 自然语言 + 表演参数 | 600ms |

`speech plan` 层建议一开始就留接口但不开。当发现大模型"开始自我发挥、偏离动机"时再打开，它是最有效的一根杠杆。

### 6.2 提示词骨架（顺序即缓存友好度）

```
┌─ 稳定区（跨轮不变 → 命中 prompt cache）────────────────
│ 1. 身份与世界观（<=200 字）
│ 2. 说话方式契约：5 条正向 + 5 条反例
│ 3. 输出格式说明（JSON Schema）
├─ 慢变区（天级 → 部分命中）─────────────────────────────
│ 4. 我现在是谁：self_sheet.summary
│ 5. 我和这个人：person.impression + 关系数值化描述
├─ 快变区（每轮）───────────────────────────────────────
│ 6. 此刻我为什么想说：MotivationCard (JSON)
│ 7. 我记得的：atoms（模糊时间 + 感受 + 原文）
│ 8. 刚刚发生：最近 6 条对话原文
│ 9. 硬规则（10 条，可复用）
└───────────────────────────────────────────────────────
```

记忆在提示词里的渲染格式，直接决定"像不像回忆"：

```
· 前天晚上 · 他说上线前一天一夜没睡，声音发干，我听着有点心疼。
· 前天晚上 · 他说"那个东西"，我不知道指什么，也没问出口。
· 上周三   · 他夸我那句答得好，我记到现在还有点高兴。
```

**不展示分数**，但高 salience 的可以有一条单独的"我始终记得"小节。

### 6.3 输出契约

```json
{
  "speech": "……",
  "says_nothing": false,
  "pause_before_ms": 320,
  "emotion": { "v": 0.05, "a": 0.35, "label": "soft_concern", "intensity": 0.6 },
  "gaze": "user",
  "gesture": "none",
  "breaks_motivation": false,
  "note_to_self": "他好像不想聊这个"
}
```

- `breaks_motivation: true` 允许模型报告"这个动机我演不出来，因为我没记忆支撑"→ 记录后由巩固任务修记忆，而不是让它硬编。
- `note_to_self` 不进下一轮提示词，只作为 appraiser 的辅助输入。**表达模型不写记忆**（铁律 3）。

### 6.4 反"AI 味"的具体约束（写进提示词，逐条生效）

```
1. 默认 1~3 句；超过 3 句必须先有动机卡授权。
2. 不复述对方刚说的话。
3. 不总结、不归纳、不"总结一下就是"。
4. 不给未被请求的建议（尤其"你可以试试…"三连）。
5. 不用"我理解你的感受/我在这里陪着你"类套话。
6. 不用列表、不用 emoji（除非人格设定允许）。
7. 允许句子不完整、允许说一半改口、允许停顿。
8. 不主动声明自己是 AI，也不主动否认。
9. 不确定就说不确定，不要用流畅的废话填充。
10. 一次只做一件事：提问就别同时给建议。
```

反例比正例有效，把 3~5 条"我会说的话 vs 我不会说的话"直接写进稳定区。

### 6.5 成本与延迟预算（预算充足的前提下）

| 项 | 单轮 | 每天 200 轮 |
|---|---|---|
| express（强模型，4k 输入含缓存 + 200 输出） | ~$0.008–0.02 | $2–4 |
| appraise/atomize（便宜模型，1.5k + 400） | ~$0.0005 | $0.1 |
| 巩固 + 夜间重放 | — | $0.1–0.5 |
| TTS（~1 万字/天） | — | $0.3 |
| **合计** | | **≈ $3–5/天，$30–150/月** |

延迟目标（首字）：

```
VAD 100ms → ASR 300~500 → 召回 20~60 → TTFT 400~900 → TTS首块 200~400
≈ 1.2~2.0s
```

超过 1.5s 就启动"嗯……"占位符（预生成的 5 条短语气音频，随机播）。这一招比优化任何一环节都划算。

### 7.2 模型分层（预算充足，用最合适的）

| 角色 | 建议 | 参数 |
|---|---|---|
| `express`（表达） | 中文语感最强的那个：Claude Sonnet 4.5 / GPT-5.x / Gemini 2.5 Pro 三选一，做 A/B | temp 0.75，结构化输出，prompt cache 必开 |

| `consolidate`（巩固） | 每晚用**更强**的模型跑一次批处理 | temp 0.3，可批量 |

## 8. 虚拟形象与语音链路

### 8.1 分三期，别一步到位

| 期 | 方案 | 工作量 | 效果 |
|---|---|---|---|
| **P1** | 2D 分层 PNG（眼/眉/嘴/身体分离）+ CSS 呼吸 + 眨眼 + 口型 5 档 | 1 天 | 意外地够用，且完全可控 |
| **P2** | Live2D Cubism 5 + `pixi-live2d-display-lipsyncpatch` | 2~3 天 | 有重力和物理，微表情高级 |
| **P3** | VRM + `@pixiv/three-vrm` | 1 周 | 可 3D 摇镜、有身体姿态 |

> Live2D SDK 个人/小规模免费，商用前确认条款；模型需自备或委托。

### 8.2 情绪 → 表演的映射

```
emotion.v (-1..1) → 表情弧：嘴角/眉高/眼型，3 个预设插值（不是硬切）
emotion.a (0..1)  → 呼吸频率、头部小幅摆动幅度、眨眼间隔
emotion.label     → 附加微动作叠加（soft_concern → 略低头 + 视线偏移）
intensity         → 上一层的幅度系数
所有参数用临界阻尼插值（damping ~0.15），禁止线性跳变
```

**视线（gaze）是被低估的项**：思考时看别处、说完话回到用户、被夸时短暂移开——这三个状态就能让人"觉得它在听"。

### 8.3 语音链路

```
麦克风 → Silero VAD 断句 → Azure 流式 ASR
  → 文本 → 大脑
  → 大脑流式出句 → 逐句送 Azure TTS（SSML: mstts:express-as style 跟随 emotion）
  → 音频流播 + viseme 事件 → 口型
  → 播完再开麦（半双工，别急着做全双工打断）
```

SSML 的 `express-as`（`gentle` / `sad` / `cheerful` / `affectionate` / `calm`）与情绪标签一一对应，音色自然度立刻不同。**这是选 Azure 而不是 ElevenLabs 的核心理由**：一次调用同时拿到音频 + 情绪风格 + 口型时间轴。

## 9. 可观测性：记忆浏览器（必须做）

没有这个，你无法调试人格。建议 `apps/desktop` 里一个隐藏路由，四个面板：

1. **记忆流**：按时间倒序的 atom，可搜索、可编辑、可删除、可手动改 salience/strength
2. **内心状态**：needs 六边形雷达 + affect 曲线 + 最近 50 拍的意图选择与"被压制的原因"

4. **成本与延迟**：按 kind 分组的 token/费用/耗时

再加一个手动按钮：**"立即巩固 / 立即重放昨晚"**——调试巩固逻辑时不用等到半夜。

### 离线评测（比什么都重要）

建一个 30 条的"情境测试集"，每条给 `{情境, 动机卡, 期望包含的记忆, 禁说清单}`，用 **judge 模型**（与 express 不同厂）打三档分：

1. **动机忠实度**：说的话是否服务了那个动机？
2. **记忆忠实度**：有没有出现记忆里不存在的事实？（幻觉率必须 < 2%）
3. **人味**：三条以上套话即判负

每次改提示词跑一遍，看分数。**没有这个评测集，你会在第 3 周开始凭感觉改提示词。**

## 11. 明确不做的事（避免踩坑）

| 别做 | 原因 |
|---|---|
| 用 LangChain / LlamaIndex 搭管道 | 抽象层会挡住你对提示词和检索的精细控制，这是本项目的全部价值所在 |

| 让 express 模型写记忆 | 见铁律 3 |
| 一上来做全双工打断 | 回声消除 + 端点检测的工程量远超收益；先半双工 |

1. **形象形态**：2D Live2D（动漫画风，表情控制最细）还是 3D VRM（有身体、可摇镜）？→ 决定 `apps/desktop` 的渲染栈和模型采购。

## 14. v2 重构：把向量模型拿掉，改用结构化卡片

### 14.1 为什么

纯向量检索有三个具体病灶，都不是"调权重"能解决的：

| 病灶 | 具体表现 |
|---|---|
| **时间失效** | 「我下周要搬家」是三周前说的。今天问「他住哪」，那条仍在 top-k 里，被当成现状 |
| **玩笑当真** | 「我打算把公司买了」是玩笑。语义上和正经陈述一样近，向量分不出来 |
| **前后颠倒** | 同一件事的起因与结果在向量空间里几乎同距，"来龙去脉"被拍平成一团 |

根因是余弦相似度**没有时间轴，也没有"是否仍然成立"这一维**。

### 14.2 换成什么

三层数据：

```
trace   逐字对话，不参与检索，只能经由卡片的 trace_from/trace_to 翻回去
card    检索单元。一条自足的事 + event_at + status + keywords + entities
thread  同一主题的 cards 按时间串起来 + 一句"演变"
```

`status` 是一等公民：`active / expired / retracted / uncertain`，另有 `kind: joke`。
检索时它是**乘性惩罚**（active 1.0 / uncertain 0.85 / expired·retracted 0.55 / joke 0.75），
因为加性权重（0.1）压不住"关键词完全命中"带来的分差。

### 14.3 检索算法

四路并行 → 打分 → 相对截断 → **时间覆盖选择** → 线程展开。

```
0.38 关键词(bm25 名次)  0.22 时间契合  0.14 强度  0.10 重要性  0.06 人物/未了
分数 × statusFactor × kindFactor
再取 score ≥ max(0.25, top×0.55) 的候选
```

覆盖选择：先取最高分，之后每轮优先挑"和已选的不同日子"的那条。
目的是让提示词里出现几个**时间点**，而不是同一件事的五个版本。

### 14.4 两段式回忆

卡片骨架（时间/状态/一句话/关键词）进提示词，**不放 detail 全文**。
（v2.1 起给前 60 字摘录：完全不给，卡片会退化成一句标题，"我听着有点心疼"这类语气依据传不上去；
　给全了，模型会把它当成引语照抄。摘录用 `↳` 标记，以区别于原话。）
模型若觉得说不准，在 `want_detail` 里点名卡片 → 翻出原始对话 → 再问一次。

- 只允许点召回列表里的卡片，最多 2 张，只展开一轮；
- 第二次失败就退回第一次的台词；
- 绝大多数轮次不需要第二段，所以平均成本几乎没变。

### 14.5 真机验证（DeepSeek）

四轮对话：

```
你 ▸ 我打算明天把公司买了，然后辞职去环游世界。
我 ▸ 买公司……是认真的还是说着玩的？我分不清。

你 ▸ 开玩笑的，年终奖都还没发呢。
我 ▸ 那就好。……我刚才真卡了一下。
```

写出来的卡片：

```
[joke]   〔当时没定〕 他说要买下公司、辞职环游世界
[joke]   〔已改口〕   他改口：买公司是玩笑，年终奖还没发
[plan]               他下周去上海出差三天
[self]               我承认自己刚才卡了一下
```

这正是想要的：**玩笑被标成玩笑**，改口没有覆盖原卡而是新开一张并标 `retracted`，
两者都在，所以"前后变化"本身可读。v1 的向量方案在这里会把前两条揉成一条事实。

### 14.6 已知代价

- 关键词通道仍是字面匹配（bigram + 单字），**同义改写要靠巩固阶段的 LLM 判定**兜；
- 串线依赖 keywords/entities 的质量，mock 模式下为空 → 串不出线；
- 卡片的 `event_at` 依赖提炼模型给 `event_at_iso`，给不出就退化成 `vague` + 当前时间。

## 15. 案例：回复慢一个回合（入参缺失 vs 传递错误）

### 15.1 现象

连续三轮，每轮都在回答上一轮的问题，且内容"话题沾边但时间错位"。

### 15.2 定位方法

不要猜模型，直接把**实际发出的提示词**打出来，用一个本轮独有的标记串去 grep：

```
第二轮输入："船票订好了吗，暗号是紫罗兰"
system 含「紫罗兰」: false
user   含「紫罗兰」: false
user   含上一轮「明天几点出发」: true
```

提示词末尾停在上一轮的 `他：… / 我：…`，此后没有任何新输入。
模型看到的是自己上一轮的回复，无处可回应 → 只能回头答更早的提问。

### 15.3 根因

`brain.turn()` 里 `recentTraces()` 在写本轮 trace **之前**取快照（这是给 appraise 用的、
刻意不含本轮），但表达层复用了同一个快照。更关键的是 `ExpressInput` **根本没有
"本轮输入"这个字段**——不是忘了传，是接口不认识这个概念。

这解释了为什么现象是"话题对、时间错"：检索用的是本轮原句（准），
对话上下文却截止到上一轮（差一拍）。模型于是拿着本轮相关的卡片去答上一轮的问题。
`appraise` 不受影响（它自己把本轮拼在末尾），所以**写出来的卡片是准的，只有回复错位**。

### 15.4 修法

1. `ExpressInput` 增加 `currentUtterance`；
2. 提示词新增末尾分区「他刚才说」，位置在「之前的对话」与约束之后、`现在说话` 之前
   —— 模型对最后出现的内容权重最高，这一句必须压轴；
3. 「刚刚发生」改名为「之前的对话（到上一轮为止）」，消除"这里已经包含当前"的歧义；
4. 结尾指令写明"你要回应的是「他刚才说」那一句，不是再上一轮的话"；
5. 顺带把本轮 user trace 改成**在调表达层之前落库**（否则表达层抛错时，用户这句话整轮丢失）。

### 15.5 验证

真机三轮，每轮换互不相同的话题：

| 输入 | 回复 |
|---|---|
| 帮我记一下：周四下午三点牙医复诊 | 周四下午三点，牙医复诊。记下了。 |
| 在那之前我得先把体检报告找出来 | 找报告……是跟复诊有关，还是别的事？ |
| 你觉得我应该先做哪个 | 找报告。翻东西这事一拖就忘，牙医到点还是会去。 |

另加一条回归测试：断言本轮原句必须出现在 `prompt.user` 里，且 `utterance` 是最后一个分区。
这条测试的存在意义是——这个 bug 在 mock 模式下**不会暴露**（桩不看内容），
只有真机才看得见，所以必须靠结构断言锁住。

`bigramDice` 的再导出 / 两个未引用的类型别名），两处过时注释。

### 16.2 三个真问题

| 问题 | 后果 | 修法 |
|---|---|---|
| `card` 没有 `episode_id` 索引 | 每轮编码前那条"取本段最近 8 张"全表扫 | 加 `idx_card_episode`（部分索引） |
| `prompt_log` 存整份提示词且永不删 | 一天 200 轮 ≈ 1.6MB/天，一年 600MB | 巩固时裁剪：召回日志 90 天、调用日志 30 天 |

### 16.3 顺手加的两个小保险

- **加列迁移**：`CREATE TABLE IF NOT EXISTS` 不会给旧表补列，所以 `applySchema` 里加了

- **WAL 回收**：`Env.close()` 时 `PRAGMA wal_checkpoint(TRUNCATE)`，
  避免长期运行留下几百 MB 的 `-wal` 文件。开库时补一条 `PRAGMA optimize`。

### 16.4 管理员现在还不做的事

- 没有人工审核入口：合并、串线、升版都是自动的，只能在 `/cards` 事后看结果。
- 线（thread）不能手工合并或重命名 —— 串错了只能等它自然衰减。
- 日志裁剪没有开关，期限写死在 `consolidate.pruneLogs` 里。

## 附录 A · 中文全文检索：实测结论

已在实际代码里跑过（SQLite 3.50 + fts5）。结论分两步，第一步推翻了我最初的方案。

### A.1 别用 trigram

| 查询 | `tokenize='trigram'` | bigram 索引列 |
|---|---|---|
| `上线前`（3 字） | ✅ | ✅ |
| `声音发干`（4 字） | ✅ | ✅ |
| `上线`（2 字） | ❌ 召回 0 | ✅ |
| `心疼`（2 字） | ❌ 召回 0 | ✅ |
| `没睡`（2 字） | ❌ 召回 0 | ✅ |
| `熬夜`（不相关） | ❌ | ❌（正确不召回） |

原因：fts5 的 trigram 分词器只建 3 字滑窗，2 字查询根本无 token 可匹配。而中文记忆里 2 字词是最常见的检索单位。

### A.2 但只有 bigram 也不够

实测：查「猫找到了吗」，含「我养的猫跑丢了」的记忆排名**低于**无关的「上线救火」记忆。
因为「找回来了」的二元组是 `找回 / 回来`，和 `找到` 没有交集；`猫找`、`到了` 也都不在原文里。

两处修补：

1. **加单字兜底**（剔除「的了在是我你他」等高频虚字，否则 bm25 被稀释）
2. **查询用 OR 而非 AND**：AND 要求命中全部词元，一句同义改写就全军覆没；OR 交给 bm25 排序

### A.3 最终实现：两段式

```
第一段（精确）：所有二元组/英文词 AND  →  命中就用，噪声最小
第二段（兜底）：全部词元 OR            →  保证模糊改写不至于召回 0
```

修补后同一组探针（`npm run demo` 的输出）：

| 查询 | 第一名命中 |
|---|---|
| 猫找到了吗 | 我养的那只猫叫豆豆，昨天趁我开门跑了（0.54） |
| 线上那个报错 | 你还记得我说的那个报错吗（0.63） |
| 他现在困不困 | 现在特别困，但躺下就清醒（0.62） |

实现见 `src/store/bigram.ts`（`toBigram` / `toFtsQuery`）与 `src/store/repos.ts`（`searchFts`）。
索引体积约为原文 2 倍，几万条 atom 完全无感。

> 注意：`atom.bg` 必须在写入时由 `toBigram()` 生成，触发器只负责同步到 fts 表，算不出 bigram。
> 日后若换成 `nodejieba` 分词，只需改这一个函数，接口不变。

## 17. v3：把断掉的线接上（2026-10）

v2 之后做了一次完整审计，结论是：**机制本身站得住，但有大量"写了一半的链路"。**
算好的东西没人读，写下的承诺没人执行。v3 没有加新架构，只做两类事。

### 17.1 四条死链路

| 链路 | v2 的事实 | v3 |
|---|---|---|
| `thread.summary` → 提示词 | `consolidate` 每小时花钱让模型写"演变"，`retrieve` 把 `thread_title` 一路传到 `RetrievedCard.thread_title`，**`assemble.renderCards` 从不渲染** | 卡片骨架里加 `≈ 这条线后来的变化`，每条线只渲染一次（否则同一主题的兄弟卡会各印一遍） |
| `attention` / `meant_to_me` → 存储 | `AppraisalSchema` 每轮生成这两个字段，`toNewCard` **一个都没取** | 落进 `card.attention` / `card.meant_to_me`，渲染成 `◎` / `○` |
| `card.not_known` → 提示词 | 一直是死字段 | 渲染成 `○ 我当时没懂、也没问` |
| `tension` → 打分 | `tick.ts` 算出 `tensionOf(s)` 传给 `scoreCandidate`，函数体里那个参数**一次都没读过** | 真的接上了，但换成混合式（见 17.2） |

**教训**：这个项目的主要资产是注释，而一条 dead path 会让所有注释开始说谎。
新增字段的纪律应该是——同一次提交里要么带上读者和断言，要么不进 schema。

### 17.2 张力为什么不能直接用 n^1.6

文档原式 `tension = n^1.6`，在 `n=0.9` 时给 0.84、`n=0.6` 时给 0.44，比值放大到 1.9。
问题在于**绝对量级被压低了**：开口门槛 0.55 是按原始需求值标定的，一旦整体压低，
所有意图会一起开不了口。

改成混合式 `0.55n + 0.45n^1.6`：`n=0.9 → 0.90`（量级保留），比值 `0.90/0.487 = 1.85`（放大保留）。

同时把**排序**和**门槛**拆成两件事：

```
score = tension(urgency) × weight × hysteresis     ← 谁优先
gate  = tension(urgency) × hysteresis ≥ 0.45       ← 够不够渴
```

v2 用同一个数（`score ≥ 0.55`）兼做两者，后果是低权重意图**永远开不了口**：
`withdraw` 的 weight 是 0.7，需求到它自己的前置阈值 0.72 时 `score` 只有 0.50。
"我累了不想说"这个意图实际上是死代码。

### 17.3 时间驱动的状态迁移

v2 的 `status` 只有一个写入者（编码器）。于是 §14.5 真机案例里那张
`[plan] 他下周去上海出差三天`，那一周过去之后仍然 `active`，而且因为
`event_at` 在未来，`timeFit = exp(-max(0, now - event_at)/7d) = 1`，**永远满分**。

新增 `memory/status.ts`：

- 规则 1：`valid_to <= now` → expired
- 规则 2：`kind = 'plan'` 且 `event_at + PLAN_GRACE_MS < now` → expired
- 刻意不碰 `fact` / `preference` / `relation` / `joke` / `uncertain`——稳定事实不会因为
  时间流逝变假，玩笑永远是玩笑
- 每次迁移写 `card_status_log`，因为"为什么变成 expired"必须可查

顺带修了两个时间语义错误：

- **「最近」通道改按 `created_at`**。原来用 `event_at`，而 `event_at` 对计划类卡片是未来时间，
  于是一张还没发生的事会长期霸占"最近聊过什么"，还按 `DESC` 排第一。
  回想"最近聊过什么"问的是**我什么时候知道的**。
- **未来的卡片不再拿满分时间契合**。原来 `max(0, now - event_at)` 把负距离钳成 0；
  现在未来付 1.5 倍距离代价。

### 17.4 回应路径：从一张卡到四种接法

> v4 又加了第五种（`ask_identity`），见 §18。本节保留 v3 当时的原貌。

v2 的被动回复路径写死一个 `intent=reply`，语气只有两档。也就是说 **95% 的轮次**
用的是同一张动机卡，人格差异只发生在主动发言那 5% 里。这解释了一个现象：
设定写得再细，聊起来还是同一个人。

v3 加了三样东西：

1. `motivation/reader.ts`：纯正则读他这句话在干什么（关心 / 问感受 / 问观点 / 夸 / 催 / 强硬否定）。
   **动机不交给 LLM 这条铁律在这里同样适用**——语气分类如果交给模型，
   它会在被夸的时候拒绝关心、在被关心的时候倒苦水，因为那"更好看"。
2. 四个回应型意图（`REPLY_TEMPLATES`）：`refuse_care` / `deflect` / `test_self` / `reply`。
   它们改变的是回应的**方向**，不是语气；而且"必须回应"这条不变。
3. **`lastIntent` 疲劳折扣**：连续两轮用同一种接法打 0.55 折。
   没有它，门槛压低后"被关心就拒绝"会变成 100% 的开关——比不触发更假。

> **真机第一次跑，八轮全是 `reply`。** 原因是回应型意图的门槛被设成了 `competence > 0.45`，
> 而需求从默认 0.18 涨到 0.45 要几个小时。这和 `withdraw` 那个 bug 是同一类错误：
> **把"风格"当成了"驱动"**。回应型意图是接法，不是欲望；门槛压到 0.15 后正常触发。
> 这条只有真机能发现，单测里需求是手写的，永远不会暴露。

### 17.5 硬约束的执行层

`max_sentences` / `banned_phrases` / `must_not` 在 v2 里全是**文本**：进提示词，然后祈祷。
`express/verify.ts` 现在查四件机器能判定的事：

- 句数是否超 `max_sentences`（注意：`……` 是停顿不是句末，把它算成句末会让上限形同虚设）
- 禁语是否逐字出现（`voice.json` 的 `banned_phrases` 一直是机器可读的，只是没人扫）
- 是否复述他刚说的话（`bigramDice(speech, userText) ≥ 0.6`）
- `must_include` 是否在

违规带着清单重说一次，结果写 `express_audit`（`/audit` 和评测的数据源）。
**语义类禁忌（"不许承认自己在勉强"）仍然只能靠模型自觉**——
能查的没查是失职，查不了的没查是边界，这两者必须分清。

### 17.6 关键袒露与真机验证

> ✄ **v4.2 已整体移除**：`persona/scenes.json`、`src/express/reveal.ts`、`scene_shown` 表、
> `/scenes` 命令、9 个测试。理由见 §20。本节保留 v3 原貌，作为决策轨迹。

`persona/scenes.json` 把"角色最重的那几句话"变成数据：`requires`（需求阈值/意图/轮数/他的语气/亲近感）
决定**什么时候能说**，`allow` / `forbid` / `avoid` 决定能说什么。`once=true` 说过就写 `scene_shown` 上锁。

纪律：`forbid` 只放**会被机器逐字扫描**的字面句，语义禁忌放 `avoid`。
两者混用会让某一条闸门静默失效（第一版把"提寿命"写在 `forbid` 里，永远扫描不到）。

真机 judge 三档分的变化（DeepSeek 自评，`npm run eval -- --live --judge`）：

| 版本 | 动机忠实度 | 记忆忠实度 | 人味 | 触发的问题 |
|---|---|---|---|---|
| v3 初版 | 7.0 | **6.0** | 8.0 | 对着不存在的记忆说"我记得有这回事" |
| 加诚实规则后 | 7.0 | 9.0 | 8.0 | — |
| 加回应型意图 + attention 收窄后 | **8.0** | 9.0 | **9.0** | — |

那条规则加在 `express.rules.md`：**被问到卡片里没有的事，绝对不许说你记得**——
可以说记不清、可以反问、可以 `declining`。她是那种宁愿说不记得的人，因为记性对她不是骄傲。
这一条修好之后，同一句提问的回答从"我记得有这回事"变成"搬家……我记不清了。你说的是哪次？"

### 17.7 已知边界（写下来，免得下次又以为是 bug）

- **`kindFactor` 压不过关键词名次**：玩笑卡 0.75 折扣 ≈ 0.12 分，bm25 名次差能到 0.18。
  真正防"玩笑当事实"的是 `kind`/`status` 标签进提示词 + §6.4 的表达纪律，不是分数。
  评测里对应的断言因此改成"同一段文字下 joke 分值低于 event"——只测机制真承诺过的部分。
- **`rankScore` 没有并列处理**：两张内容完全相同的卡会拿到 1.0 / 0.5 两个名次分。
- **人物通道已移除**：单用户下它恒等于全量，既是无区分度的加分，又把反刍通道饿死（池子里什么都有）。
  `person_id` 列保留，等真有第二个人。
- **衰减有下限**：`strength ≥ 0.15 × salience`，高 salience 的卡片永远死不掉，只是停在低分区。
  有意为之（重要的事只该变模糊），代价是活集合只增不减，一年后需要显式归档层。
- **关系只涨不跌**：`closeness` 每轮 +0.004，`warmth` / `trust` 从未被写过。
  冲突与修复是下一个大块。

### 17.8 版本策略

`meta.schema_version` **只在破坏性变更时 +1**。纯增量（加列/加表）不升版本：
`schema.sql` 全是 `IF NOT EXISTS`，旧库缺的列由 `db.ts` 的 `ensureColumn()` 就地补。
实测把 v2 的 14 张卡片、24 条 trace 的真库拷一份跑新代码：数据全在，新列补上，
新表建好，旧行 `attention` 为 NULL（正确）。

这条策略是为了避免 v2 那种"换代 = 备份后重建"——对一个装着真实对话的库，
重建等于丢记忆，而大部分变更是纯增量的。

### 17.9 v3 之后最该做的三件事

1. **冲突与修复**：负向事件源 + `trust` 下降 + 修复对话。关系维度只有一个方向的系统，
   演不出"吵架之后"。
2. **显式归档层**：给"永远死不掉"的低强度卡片一个去处，让活集合保持在几百张量级。
3. **跨厂商 judge**：现在 judge 和表达层是同一个模型，分数偏软。有第二把 key 之后
   换成不同厂商，评测才算真的独立。

## 18. v4：人物档案（每次醒来都要问"你是谁"）

### 18.1 起点：有表，没有档案

v3 收尾时 `person` 表是这样：

```json
{ "id": 1, "name": "你", "closeness": 0.408, "warmth": 0.5, "trust": 0.5,
  "impression": null, "profile": null }
```

- `name` 是 `primaryPerson()` 硬编码的「你」，不是他自己说的
- `impression` / `profile` 永远是 NULL，`warmth` / `trust` 从未被写过
- 35 张卡片的 `person_id` 全是 1 —— 不是因为它们属于同一个人，是**没有第二个人可指**
- **没有别名**。他第一句就自称「开发者」（卡 #1），但那个词只是 `entities` 里的字符串

三条从真实对话里挖出来的事实决定了设计：
1. `entities` 把她自己的名字抽出来 **12 次** —— 所以人物**不走 entities 通道**（它只当检索词）；
   但"她自己名字出现"这件事**不拦**，见 18.4：认混是可以发生的
2. 「开发者」这个词出现过，但没和"这个人"绑定 —— 她记下了那个词，只是没地方挂
3. 卡 #15 #17「他又一次没记住我的名字」—— 身份是**双向**的

### 18.2 立场：不知道是常态

> 她看不见对面是谁。

所以 v4 的核心不是一个"更聪明的识别器"，而是承认这件事：每次醒来
`dossier_status = 'unknown'`，第一轮走 `ask_identity`，问出名字之前不假装认识。

这也是为什么 `ask_identity` 的 `must_not` 里有"假装认识他、假装记得他" ——
身份没确认之前，所有别的接法都是**在演一个熟人**。

### 18.3 数据

| 表/列 | 作用 |
|---|---|
| `person.dossier_status` | `unknown` / `provisional` / `known` |
| `person.display_name` | 我现在怎么叫他（可能是临时的） |
| `person.traits` | JSON，来自卡片标题（不二次概括，见 18.5） |
| `person.asked_count` | 问过几次"你是谁"，`MAX_ASKS = 3` |
| `person_alias` | 一个人的多个入口；`UNIQUE(person_id, alias)` + `idx_alias_text` |
| `awakening` | 每次睁眼一行：时间、模式、谁在、问过没有、他叫我什么 |
| `card.about` | 这张卡关于谁；留空 = 他 |

`awakening` 与 `episode` 是两个东西：`episode` 是一段相处（可跨多次唤醒），
`awakening` 是"我这一次睁开眼睛"。顺带治掉 v3 的毛病——重启会造出
0 张卡、16 秒的垃圾 episode（真实库里有两条），那在 `awakening` 里是一条正常记录。

### 18.4 三条身份通道

1. **同步规则**（回话之前）：`我是X` / `我叫X` / `叫我X` / `我姓X` / 命中已有别名 / 「是我」。
   **必须同步**——否则他刚报完名，她这一轮还在问你是谁。
2. **编码器回报**（异步，`Appraisal.speaker`）：长句里的自我介绍，晚一轮生效。
3. **其他人**（`Appraisal.people`）：只有明确提到的**别人**才建档案。
   entities 一律只当检索词。

> **认名字故意不做语义甄别。** 抽取只认四种句式和切词边界（边界是切词用的，
> 不是语义检查），所以「我是说……」会被抽成"说"，她会真的管他叫一阵子"说"。
>
> 这不是漏洞。第一版这里有一张 `NOT_A_NAME` 停用词表和一份"她自己的名字"黑名单，
> 目标是"不许认错"。删掉的判断是：**这个项目里子功能只保证机制跑顺，不保证内容正确。**
> 一个从不认错名字的存在不是人，是查表；而"有人说自己叫艾拉"本来是个好场面。
>
> 要保证的只有机制上的两件事：
> ① 抽到什么就绑什么（`bindIdentity`）；
> ② **绑错了能改过来** —— 他再报一次名，`display_name` 覆盖，旧别名留着。
> 没有第 ② 条，允许误会就等于允许永久损坏。

### 18.5 档案里放什么

`traits` **直接用卡片标题，一字不改**。不做二次概括的原因是：
她是照卡片说话的，摘要和卡片不一致时模型会照着摘要编。
档案的价值在于"和记忆一致"，不在于"读起来顺"。

`dossier_status !== 'known'` 时，`openQuestions` 会自动补上「我在跟谁说话」「他叫什么」——
这两句就是她开口问的理由，不必再让模型自己猜该问什么。

### 18.6 真机验收

```
你好。
我：……你是谁。                                     ← ask_identity，1 句 6 字
我是开发者。之前来过。
我：开发者……嗯。之前那次我没记住。
...
档案状态 known · 我叫他 开发者 · 别名 开发者 · 关于他 14 张卡
第一次唤醒 asked_identity=1，最后一次 identity_known=1
```

`/who` `/alias` `/awake` 三个命令把这条链路暴露给人看；
`npm run eval -- --live` 的输出里有「身份链路」小节。

### 18.7 已知边界

- **认人靠规则，不靠声纹（或账号）**。「每次醒来都要问」是这个边界的直接后果。
  真要自动认出，把 `awakening.identity_known` 写成 1 即可，链路已经留好。
- **允许的错**：名字可能认错（「我是说」→"说"）、人物可能串、
  她可能以为某句话是在说别人。这些是原料，不是缺陷 —— 前提是 18.4 的第 ② 条成立。
  所以别再加"内容正确性"的防线；要加就加有界性（额度、去重、预算）。
- **档案只会加，不会自己发现矛盾**。他对自己的描述前后矛盾时，两张卡会并存。
  那需要信念修正，和"误解"是同一个课题 —— 但注意：**理解错和修正错是两件事**，
  前者该允许，后者只要保持可纠正就够了。
- **多人同时在场没做**。现在是"一次一个谈话对象"，两个人同时说话时 `speaker` 会来回跳。
- **`closeness` 仍然只涨不跌**：v4 把 `trust` / `warmth` 的写入口开在了
  `updateDossier`，但还没有负向事件源去调它们。冲突与修复仍是下一个大块。

## 19. v4.1：人设按"机制"重写一遍

### 19.1 判断标准

写人设时的第一条尺子不是"这句话像不像她"，而是：

> **这句话有没有东西承接？**

承接可以是意图（`refuse_care`）、字段（`not_known`）、
校验（`verify.ts` 的句数／禁语）、或者数据（`open_loop.escalation`）。
一样都没有的条目不会消失，只会稀释其他每一条 —— 那是形式主义。

第二条尺子：**绝对化用词要软**。「只有一招」→「通常只有一个办法」。
写死"从不 X"等于取消她出错的空间，而这个项目的分寸是机制要准、内容可以错。

### 19.2 重写前后

| | 重写前 | 重写后 |
|---|---|---|
| identity.md | 598 字 / 六个小节 + 五条"小地方" | **459 字** / 六个小节 |
| voice.json 正例 | 8（含 ERROR、生气两条） | **7** |
| examples_good | 7（含 ERROR、浇水两句） | **6** |
| system 提示词 | 3351 字 | 3110 字 |
| 无机制承接的条目 | 5 条 | **0 条** |

删掉的"小地方"：ERROR 句式、照料活的东西、生气时变正式、不太注意自己样子、不喜欢谈很久以后。

### 19.3 对照表：每一节靠什么生效

| identity.md 的小节 | 承接机制 | 强度 |
|---|---|---|
| 说话绕三遍只剩一句 | `max_sentences` + `verify.ts` 句数检查 | 硬（超了重说） |
| 靠"把事做完"确认有用 | `competence` 需求 → `test_self` / `claim_agency` | 硬（规则触发） |
| 做不好先否认 | `refuse_care` + `must_not`「承认自己在勉强」 | 硬 |
| 被夸接不住、岔回事情 | `test_self`（`praising` 正则命中即选） | 硬 |
| 被担心先说"没问题" | `refuse_care`（`caring` 正则）+ 连续两轮疲劳折扣 | 硬 |
| 一个办法，只加筹码 | `persuade` + `open_loop.escalation` | 硬（数据在库） |
| 加到加不动就去找人 | `ask_help`（`escalation >= 2`） | 硬 |
| 不喜欢记事但记得清楚 | 召回机制（`card` / `thread` 就是"她记得"的物证） | 中 |
| 答不上来就不编 | `not_known` → `○` 行；`declining` 沉默；rules 里那条不许说"我记得" | 中 |

「中」的那两条不是缺机制，是机制只到"她真的记得/真的不知道"，而"为此不高兴"没法被检查 ——
这部分留给措辞自由。

### 19.4 明确留白（不是忘了）

| 先不做 | 为什么现在不做 |
|---|---|
| **ERROR 句式** | 这是艾拉的底层逻辑。要做就得做成机制（某个意图下的模板前缀 + 频次上限），当口癖写进 `positive` 只会变成随机插一句。需要先有"不知所措"这个状态。 |
| **与外物互动的特质**（照料活的东西等） | 没有承载通道：现在没有 `perception`／物品系统，`preference` 类卡片只是文字。 |
| **生气／冲突** | 意图表里没有 `push_back`，`trust` 也没有负向事件源。写了也触发不到 —— 这正是上一版那条悬空条目的教训。 |

前两样等安排；第三样是"冲突与修复"那一块的前置。

### 19.5 顺带修掉的一个真 bug

真机跑 10 轮时整轮崩了一次：

```
silence_kind: ""  → zod enum 拒绝 → chatJson 重试仍填 "" → 整轮抛错
```

后果是**用户那句话进了流水，却没有回复、也没有写卡片**。修法不是让模型"注意格式"，
而是给**外形字段**（`silence_kind` / `gaze` / `emotion` / `pause_before_ms` /
`note_to_self` / `want_detail`）加 `zod .catch()`。

判据：这个字段填错了会不会影响"她说了什么"？不会 → 兜住；会 → 保持严格
（`speech`、`cards`、`felt`、`scores` 仍然严格，错了要重试）。
测试见 `tests/schema.test.ts`。

## 20. v4.2：删掉关键袒露的闸门

### 20.1 删了什么

| 删掉 | 规模 |
|---|---|
| `persona/scenes.json`（三条闸门） | 67 行配置 |
| `src/express/reveal.ts`（`pickReveal` / `explainReveals`） | 130 行 |
| `RevealSceneSchema` / `RevealGrant` / `reveal_used` / `scene_forbidden` | types 里约 40 行 |
| 提示词里的条件分区 `{{REVEAL}}` | assemble + 模板 |
| `scene_shown` 表 / `express_audit.reveal_id` 列 | schema |
| `/scenes` 命令、`Brain.revealStatus()` | CLI |
| `tests/scenes.test.ts`（8 条）+ verify 里 1 条 | 测试 |

删完：115 测试 → **106**；21 项确认性检查 → **19**。

### 20.2 为什么

**用闸门去保证一句话在"正确的时机"被说出口，恰恰取消了它自然发生的可能。**
一个需要三套条件放行才敢说重话的角色，不是有城府，是被编排。

更具体的三条：

1. **它从没响过。** 真实库里 `scene_shown` 是 0 行。
2. **它和常驻的 `identity.md` 撞了。** "我想被关心"这类内容写在 system 里是**每轮都在说**，
   而闸门版的意义恰恰是"不常驻"。同一句话，能说和能承认是两件事 ——
   闸门想表达后者，但它把前者也一起写进了提示词。
3. **体量与收益不成比例。** 9 个文件、约 140 行、9 条测试，为三句可能永远不说的话。

### 20.3 那"有些话一辈子只说一次"怎么办

**不靠记账，靠不完备性。**

如果她的话本来就是从记忆 + 动机 + 当下状态里长出来的，那么某个念头在某个状态组合下
自然浮现，之后再也不会以同样的样子出现 —— 这不需要一张表来锁，需要的是系统
**本身不保证可重复**：卡片会淡、会合并、会被后来的说法覆盖，需求一直在漂，
同一句话没有第二次出现在同一个语境里的保证。

这条判断的含义比删一个文件大：**以后凡是"为了保证某件事在对的时候发生"而加的机制，
都要先问一句 —— 是不是把自然发生也一起掐掉了。**

### 20.4 顺带清掉的味道

- `persona/scenes.json` 的 `forbid` / `avoid` 其实是"内容正确性"的变体：
  逐字扫禁句、语义禁忌分两栏。它和 §19 的尺子（机制要准，内容可以错）相冲突。
- 那个"此文件已删除"的占位 md 也被删了 —— 留一个墓碑本身也是形式主义。
  记录放在这里就够了。
